# 가상 반려동물 게임 통합 기획서

> 목적: Work 환경에서 MVP 구현을 바로 시작하기 위한 제품·기술 기준 문서  
> 작성 기준: 2026-10-27  
> 상태 표기: **확정**은 대화와 현재 요청에서 명시된 방향, **제안**은 구현 가능한 초기값, **미결정**은 제품 판단이 필요한 항목이다.

## 1. 제품 개요

사용자는 강아지 또는 고양이를 입양해 일상적으로 돌본다. 반려동물은 사용자가 접속하지 않아도 욕구와 성향에 따라 생활한다. 재접속하면 서버가 지난 시간의 활동을 복원하고, 홈캠 화면과 짧은 생활 기록으로 그 결과를 보여준다. 사용자의 먹이·놀이·훈련은 상태에 영향을 주지만 모든 행동을 직접 지시하지는 않는다.

### 제품 우선순위

1. **자율성(확정):** 접속 여부와 무관하게 반려동물이 스스로 활동하며, 같은 입력에도 성향과 상태에 따른 차이가 난다.
2. **실재감(확정):** 행동에 원인이 있고, 시간·공간·욕구·관계가 일관되며, 홈캠과 기록이 실제 시뮬레이션 결과를 반영한다.
3. **표현 품질(제안):** 시뮬레이션을 먼저 완성하고 화면 표현을 단계적으로 높인다.

핵심 경험은 “내가 없는 동안에도 이 아이가 자기 삶을 살았다”는 감각이다. 단순 랜덤 애니메이션이나 미리 만든 영상만으로 상태를 꾸미지 않는다. 렌더링 방식이 무엇이든 서버의 상태와 사건이 단일한 사실 원천이다.

## 2. 결정 사항과 범위

| 항목 | 상태 | 기준 |
|---|---|---|
| 강아지·고양이 입양 | 확정 | MVP에서 두 종 중 선택 |
| 홈캠, 먹이, 놀이, 훈련 | 확정 | 핵심 사용자 행동 |
| 자율 생활 | 확정 | 이벤트 기반 오프라인 시뮬레이션과 접속 시 상태 복원 |
| 실제 집 다중 사진 업로드·공간 재구성 | 확정된 후속 단계 | MVP 제외. 공간 모델을 교체할 수 있게 데이터 구조만 준비 |
| 3D 대 생성형 AI 렌더링 | 비교 필요, 선택 보류 | MVP 렌더러 최종 결정 전 기술 실험 |
| Spring Boot / Next.js / PostgreSQL | 확정 | 서버 / 웹 / 주 데이터베이스 |

### MVP에 포함

- 단일 사용자 계정 또는 개발용 사용자 식별, 반려동물 한 마리 입양, 이름·종·초기 성향 생성.
- 기본 방 1~2개와 정해진 가구·활동 위치. 사진 기반 실제 집 복원은 포함하지 않는다.
- 배고픔, 에너지, 기분, 청결, 친밀도, 스트레스 등 최소 상태와 시간에 따른 변화.
- 수면·이동·탐색·휴식·장난감 놀이·식사 등 자율 행동, 홈캠 현재 상태, 지난 활동 타임라인.
- 먹이 주기, 함께 놀기, 기초 훈련. 각 행동의 비용·쿨다운·상태 변화를 명시.
- 이벤트 저장, 접속 시 경과 시간 복원, 중복 요청 방지, 기본 운영 로그와 자동 테스트.

### MVP에서 제외

다중 반려동물, 친구 방문·소셜, 결제, 자유로운 가구 배치, 질병·사망, 실시간 영상 스트리밍, 장기 대화형 AI, 실제 집 사진 업로드 및 3D 재구성, 초고품질 생성 영상. 이후 확장 여부를 별도로 결정한다.

## 3. 사용자 흐름과 화면

1. **첫 접속:** 서비스 소개 → 강아지/고양이 선택 → 이름 지정 → 기본 성향과 집 생성 → 입양 완료.
2. **홈캠:** 현재 방·위치·행동·상태 단서를 표시한다. 상태에 근거한 애니메이션 또는 장면을 사용한다. 데이터 동기화 시각을 노출한다.
3. **돌봄:** 먹이 종류와 양 선택, 놀이 시작, 훈련 항목 선택 → 서버가 조건 검사와 이벤트 기록 → 변경된 상태·반응 표시.
4. **재접속:** 마지막 확정 시각부터 상태 복원 → 중요한 사건을 요약한 “부재 중 기록” → 현재 홈캠으로 이동.
5. **기록:** 시각, 행동, 위치, 원인 또는 결과를 간결하게 보여준다. 무의미한 반복 사건은 묶는다.

### 주요 수용 기준

- 24시간 미접속 후 재접속해도 상태가 일관되며, 같은 사건이 두 번 적용되지 않는다.
- 사용자가 홈캠에서 본 행동과 활동 기록·현재 상태가 모순되지 않는다.
- 먹이·놀이·훈련의 성공 또는 거절은 이유를 설명할 수 있다(배부름, 피로, 스트레스 등).
- 성향이 다른 두 반려동물은 같은 환경에서도 행동 분포에 관찰 가능한 차이가 있다.
- 브라우저를 새로고침하거나 API를 재시도해도 돌봄 행동이 중복 적용되지 않는다.

## 4. 시뮬레이션 규칙

### 상태

0~100 범위의 정규화된 수치로 시작하되 밸런스 값은 설정 파일에서 조정한다. `hunger`는 높을수록 배고픔, `energy`는 높을수록 활동 가능, `mood`와 `bond`는 높을수록 긍정, `stress`는 높을수록 불안이다. `cleanliness`는 높을수록 깨끗하다. 종별 차이와 개체별 성향(`activity`, `sociability`, `curiosity`, `trainability`)은 별도 보관한다. 나이와 성장 단계는 MVP에서는 표시만 하거나 고정해도 된다.

상태 수치는 행동 선택의 입력이다. 플레이어가 보게 되는 표현은 숫자 전체보다 “졸려 보임”, “배가 고픔” 같은 해석 가능한 단서가 기본이다. 디버그 화면에서는 실제 값을 확인한다.

### 행동 선택

자율 행동의 후보는 수면, 휴식, 배회, 탐색, 장난감 놀이, 식사, 그루밍, 주인 기다리기 등이다. 모든 행동은 `precondition`, 예상 지속 시간, 상태 변화, 위치 이동, 쿨다운을 가진다. 후보 점수는 욕구 해소량, 성향 선호도, 시간대, 직전 행동 반복 패널티, 환경 접근성, 작은 난수 항으로 계산한다. 난수 시드는 반려동물 ID와 시뮬레이션 구간·이벤트 번호에서 얻어 재현 가능하게 한다.

예시: `score(action) = needGain + personalityFit + contextFit - repetitionPenalty + boundedNoise`. 위험하거나 불가능한 행동은 점수를 낮추는 대신 후보에서 제외한다. 일정 조건에서는 수면·식사 등 필수 행동의 우선순위를 보장한다. 유저 행동 직후에는 반응 이벤트를 우선 처리하되, 피로·배부름 때문에 거절할 수 있다.

### 이벤트 기반 오프라인 복원

**확정된 방향:** 서버가 매 순간 전 개체를 실시간 계산하는 대신, 마지막 확정 시점과 현재 시각 사이를 접속 또는 명령 처리 시 복원한다. 예약 이벤트가 필요하면 작업자가 깨어날 수 있지만 정합성은 복원 로직만으로 보장한다.

1. 반려동물 행을 잠그고 `simulated_until` 및 버전을 읽는다.
2. 서버 UTC 시각까지의 경과 시간을 최대 복원 한도 내에서 구간으로 나눈다.
3. 현재 진행 중인 행동의 종료, 욕구 변화, 임계치 도달, 다음 행동 결정 중 가장 가까운 사건 시각으로 전진한다.
4. 사건마다 상태 변화와 위치를 확정하고 이벤트를 기록한다. 짧고 반복적인 사건은 요약 이벤트로 압축한다.
5. 현재 시각까지 처리한 뒤 스냅샷 상태·`simulated_until`·버전을 같은 트랜잭션에 저장한다.
6. API는 현재 상태와 `asOf`, 요약 사건, 다음 예상 행동 종료 시각을 반환한다.

복원 범위가 매우 길면 시간 구간별 집계와 안전한 평형 상태로 수렴시켜 무한 루프와 이벤트 폭증을 막는다. `simulated_until`은 절대 뒤로 가지 않는다. 시간 계산은 서버 UTC를 사용하고 사용자 현지 시간은 표시와 일과 패턴에만 적용한다. 클라이언트 시계는 권위가 없다.

### 구체적 돌봄 규칙(초기 제안)

| 행동 | 선행 조건 | 즉시 효과 | 장기 효과 |
|---|---|---|---|
| 먹이 주기 | 일정 쿨다운, 식사 가능 위치 | 배고픔 감소, 기분 변화 | 과식 방지; 종류별 선호도 학습 가능 |
| 함께 놀기 | 에너지·스트레스 허용 범위 | 기분·친밀도 증가, 에너지 감소 | 놀이 선호와 관계 변화 |
| 기초 훈련 | 과도한 피로·스트레스 없음 | 성공 확률에 따른 반응 | 명령별 숙련도 증가, 친밀도·스트레스 영향 |

훈련 성공 확률은 숙련도, `trainability`, 기분, 피로, 최근 반복을 이용한다. 성공·실패 어느 쪽도 무조건적인 벌점으로 표현하지 않는다. 세부 수치·쿨다운은 플레이테스트 후 조정한다.

## 5. 렌더링 전략과 보류된 선택

| 방식 | 장점 | 제약 | MVP 판단 기준 |
|---|---|---|---|
| 실시간 3D | 위치·행동·시점의 연속성, 상호작용과 일관성 | 모델·애니메이션 제작 비용, 웹 성능 | 저사양 기기에서 충분히 부드럽고 제작 가능하면 유력 |
| 생성형 AI 이미지·영상 | 분위기와 시각 다양성, 실제 집 재현 가능성 | 비용·지연·캐릭터 일관성·행동 정합성·안전성 | 동일 개체·공간·상태를 안정적으로 표현하는지 검증 |
| 2D/경량 장면 표현 | 가장 빠른 규칙 검증과 운영 | 시각적 실재감 한계 | MVP 기본 대안으로 즉시 사용 가능 |

**선택 보류:** 3D와 생성형 AI 중 어느 쪽을 최종 렌더러로 쓸지 확정하지 않는다. 구현은 `SceneState`(반려동물 외형 식별자, 방, 위치, 행동, 방향, 표정, 시각, 조명)를 서버 계약으로 두고 화면 렌더러를 교체 가능하게 만든다. 1~2주 기술 실험에서 동일한 20개 시나리오를 표현하고 개발 기간, 로딩 시간, 비용, 외형 일관성, 상태와의 일치율을 비교한다. 초기 MVP가 빠르게 필요하면 경량 2D/사전 제작 장면으로 시작한다. 생성형 AI 결과물은 권위 있는 상태를 변경하지 않는다.

## 6. 실제 집 공간 재구성: 후속 단계

사용자가 실제 집의 여러 사진을 업로드하고 공간을 재구성하는 기능은 별도 단계다. 한 장 사진으로 전체 구조를 임의 추정하는 것을 제품 약속으로 삼지 않는다. 촬영 가이드, 사진 간 중복 영역, 공간 연결·방 크기 확인, 사용자의 수동 수정 UI가 필요하다. 원본 사진은 사적인 실내 정보이므로 접근 통제, 보관 기간, 삭제, 메타데이터 처리 정책을 설계한다.

미래 확장을 위해 MVP의 공간은 `Home -> Room -> Zone/Object`로 모델링한다. 반려동물의 위치는 자유 좌표뿐 아니라 의미 있는 `zoneId`로 기록한다. 후속 업로드 과정은 `upload -> 검증 -> 재구성 초안 -> 사용자 검토/수정 -> 공간 버전 발행`으로 나누고, 새 공간 버전 적용 시 기존 반려동물 위치를 유효한 구역으로 매핑한다.

## 7. 기술 구조

```text
Next.js 웹 (입양·홈캠·돌봄·기록)
       │ HTTPS / JSON, 필요 시 SSE
Spring Boot API (인증·명령·조회·시뮬레이션 도메인)
       │ 트랜잭션
PostgreSQL (반려동물 스냅샷·이벤트·공간·멱등성 키)
       └ 선택: 오브젝트 스토리지(향후 사진·생성 자산)
```

Spring Boot에서 시뮬레이션 코어는 시간·난수·저장소 인터페이스를 주입받는 순수 도메인 모듈로 분리한다. API 계층은 입력 검증과 권한 확인, 서비스 계층은 트랜잭션·동시성, 코어는 상태 전이와 이벤트 생성에 집중한다. Next.js는 상태의 권위가 없으며 서버 응답을 화면에 투영한다. 실시간 갱신은 MVP에서 짧은 폴링으로 시작하고, 필요 시 SSE로 바꾼다.

| 엔터티 | 주요 필드 | 역할 |
|---|---|---|
| `users` | `id`, `created_at`, 인증 식별자 | 소유권 |
| `pets` | `id`, `owner_id`, `name`, `species`, `appearance_key`, `traits_json`, `created_at` | 반려동물 고정 정보 |
| `pet_state` | `pet_id`, 상태 수치, `room_id`, `zone_id`, `current_action`, `action_ends_at`, `simulated_until`, `version` | 현재 스냅샷, 반려동물당 1행 |
| `pet_events` | `id`, `pet_id`, `occurred_at`, `event_type`, `payload_json`, `sequence`, `source` | 복원 가능한 주요 이력과 기록 |
| `homes` / `rooms` / `zones` | `id`, `owner_id`, `version`, 명칭, 연결·접근 규칙 | MVP 기본 공간과 향후 실제 집 확장 |
| `training_progress` | `pet_id`, `skill_key`, `level`, `attempts`, `successes` | 명령별 숙련도 |
| `action_requests` | `owner_id`, `idempotency_key`, `request_hash`, `response_json`, `created_at` | 네트워크 재시도 중복 방지 |

외래 키와 `owner_id` 범위를 강제한다. `(pet_id, sequence)`와 `(owner_id, idempotency_key)`는 고유 제약을 둔다. 조회용으로 `pet_events(pet_id, occurred_at DESC)` 인덱스를 둔다. `payload_json`은 유연한 사건별 내용에만 사용하고 핵심 조회 필드는 정규 컬럼으로 유지한다. 이벤트 삭제·수정 정책과 장기 보관 기간은 별도 결정한다.

## 9. API 초안

모든 시각은 ISO 8601 UTC, ID는 UUID, 오류는 안정적인 `code`와 사용자 메시지를 포함한다. 인증 방식은 착수 시 선택한다. 모든 쓰기 API는 소유권 검사와 `Idempotency-Key` 헤더를 사용한다.

| 메서드·경로 | 용도 | 주요 응답 |
|---|---|---|
| `POST /api/v1/pets` | 입양 (`species`, `name`) | 반려동물과 초기 상태 |
| `GET /api/v1/pets/{id}` | 기본 정보와 최신 상태 | `pet`, `state`, `asOf`, `version` |
| `GET /api/v1/pets/{id}/homecam` | 상태 복원 후 장면 조회 | `sceneState`, `stateHints`, `asOf` |
| `GET /api/v1/pets/{id}/events?cursor=&limit=` | 부재 중/일반 기록 | 사건 목록, 다음 커서 |
| `POST /api/v1/pets/{id}/actions/feed` | 먹이 주기 | 적용 사건, 새 상태 |
| `POST /api/v1/pets/{id}/actions/play` | 함께 놀기 | 적용 사건, 새 상태 |
| `POST /api/v1/pets/{id}/actions/train` | 명령 훈련 | 결과, 숙련도, 새 상태 |
| `GET /api/v1/pets/{id}/training` | 훈련 현황 | 명령별 숙련도 |

명령 처리 순서: 인증·소유권 확인 → 멱등성 키 조회 → 상태 잠금 → 현재까지 복원 → 선행 조건 검사 → 명령 이벤트·상태 반영 → 한 트랜잭션에 저장 → 응답 캐시. 조건 불충족은 `409`와 명확한 이유 코드를 반환한다. 과도한 입력은 `429` 또는 도메인 쿨다운 오류로 구분한다.

## 10. 동시성·정합성·운영

- 한 반려동물의 상태 갱신은 DB 행 잠금(`SELECT ... FOR UPDATE`) 또는 낙관적 버전 비교 중 하나로 직렬화한다. MVP는 행 잠금이 단순하다.
- 복원과 사용자 명령을 같은 트랜잭션에 둔다. 동시에 열린 여러 탭 중 하나만 해당 구간을 적용한다.
- 동일 멱등성 키·동일 요청 본문은 저장된 응답을 반환하고, 같은 키에 다른 본문은 충돌로 처리한다.
- 이벤트 `sequence`는 반려동물별 단조 증가, `simulated_until`은 단조 증가다. 트랜잭션 실패 시 모두 롤백한다.
- 긴 복원은 작업량·시간 상한을 두고 요약 규칙으로 처리한다. DB 잠금 시간과 p95 응답 시간을 관찰한다.
- 로그에는 `petId`, 요청 ID, 복원 기간, 생성 사건 수, 시뮬레이션 버전, 지연을 남긴다. 개인 사진과 인증 정보는 로그에 넣지 않는다.
- 규칙 변경 시 `simulation_rule_version`을 이벤트 또는 스냅샷에 기록해 과거 결과 해석과 마이그레이션을 가능하게 한다.

## 12. 구현 로드맵

### 단계 0 — 결정·기술 실험

상태 변수와 행동 6~8개의 초기값을 정한다. 3D/생성형 AI/경량 표현을 같은 시나리오로 비교한다. 인증 방식과 MVP 배포 환경을 선택한다. **산출물:** 시뮬레이션 규칙표, 렌더러 선택 기준, API 계약 초안.

### 단계 1 — 시뮬레이션 세로 절편

Spring Boot와 PostgreSQL 프로젝트, 마이그레이션, 입양, 상태 스냅샷, 이벤트 저장, 가짜 시계 기반 복원, 동시성 보호를 만든다. 테스트에서 오프라인 24시간 복원과 멱등성을 통과시킨다.

### 단계 2 — 사용자 MVP

Next.js 입양·홈캠·기록 화면과 먹이·놀이·훈련 API를 연결한다. 기본 방 장면과 반려동물 행동 표현을 넣고 실제 시나리오 플레이테스트로 밸런스를 조정한다.

### 단계 3 — 품질·운영

장기 부재 압축, 오류·성능 관찰, 모바일 화면, 접근성, 데이터 삭제, 운영자 디버그 도구를 정리한다. 렌더러 기술 실험 결과에 따라 시각 품질을 올린다.

### 단계 4 — 후속 확장

다중 사진 업로드, 실내 공간 재구성, 사용자 검토·수정, 공간 버전 전환을 별도 프로젝트로 진행한다. 실제 집 자료의 보안·삭제 절차와 재구성 실패 복구를 선행한다.

## 14. 미결정 사항과 착수 전 질문

1. **렌더러:** 3D, 생성형 AI, 경량 2D 중 MVP 최종 방식. 기술 실험 후 결정한다.
2. **타깃 플랫폼:** 모바일 웹 우선 여부, 데스크톱 비중, 저사양 기준.
3. **인증:** 이메일/소셜 로그인 또는 초기 게스트 계정, 데이터 이전 정책.
4. **게임 톤:** 현실적인 돌봄과 부담 없는 캐주얼 경험 사이의 목표 지점. 방치 시 상태 하한과 알림 정책.
5. **시간 설계:** 실제 시간과 게임 시간 비율, 수면·활동의 현지 시간대 반영 방식.
6. **종별·개체별 차이:** 품종/외형 선택 범위, 성향 공개 수준, 입양 후 재설정 가능 여부.
7. **훈련 범위:** MVP 명령 목록과 숙련도 성장 속도.
8. **운영 목표:** 목표 동시 사용자, p95 지연, 사건 보관 기간, 호스팅·예산.
9. **향후 실제 집 기능:** 사진 수·촬영 가이드, 재구성 정확도 기준, 사용자 편집 범위, 원본 보관 정책.

## 15. Work에서 바로 시작할 구현 순서

1. 저장소를 `backend/`(Spring Boot), `frontend/`(Next.js), `docs/`로 구성하고 PostgreSQL 로컬 실행·마이그레이션을 준비한다.
2. 시뮬레이션 코어의 `PetState`, `Action`, `Event`, `Clock`, `RandomSource` 계약을 먼저 정의한다.
3. 가짜 시계를 이용한 “입양 후 24시간 복원” 테스트를 작성하고 복원 엔진을 구현한다.
4. 상태·이벤트 영속화와 행 잠금·멱등성 처리를 연결한다.
5. 입양·홈캠·기록·먹이·놀이·훈련 API를 순서대로 만든다.
6. Next.js에서 세 가지 핵심 화면을 연결하고, 장면은 `SceneState`만 읽어 표시한다.
7. 동시 요청과 장기 미접속 시나리오를 통과시킨 뒤 행동 빈도·상태 변화 속도를 플레이테스트로 조정한다.

첫 구현 완료 기준은 **입양한 반려동물이 사용자가 없는 24시간 동안 일관된 행동 이력을 만들고, 재접속 시 홈캠과 기록에 같은 현재 상태가 보이며, 세 가지 돌봄 행동이 중복 없이 반영되는 것**이다.
